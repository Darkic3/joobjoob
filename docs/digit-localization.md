# بومی‌سازی ارقام (Digit Localization) — معماری، قانون و روش رفع باگ

> نسخه: ۲ — سمت‌سرور + سمت‌کلاینت (بدون چشمک)
>
> این سند مرجعِ حل «چشمکِ انگلیسی→فارسی» (و برعکس) اعداد در کل سایت است.
> اگر دوباره جایی رقم‌ها اول انگلیسی دیده شدند و بعد فارسی شدند، اول این سند را
> بخوان و بخش «چک‌لیست عیب‌یابی» را اجرا کن.

---

## ۱) مشکل چیست؟

هر جایی که یک عدد با **ارقام لاتین** ساخته شود و بعداً توسط JS به **ارقام
فارسی/عربی** تبدیل شود، کاربر لحظه‌ای رقم لاتین را می‌بیند (چشمک). نمونه‌های
دیده‌شده:

- اعلان‌ها (دراپ‌داون زنگوله و صفحهٔ اعلان‌ها): «سفارش #123 …» که چند لحظه بعد
  «#۱۲۳» می‌شود؛
- قیمت‌ها، تعدادها، تاریخ‌ها و بج‌های صفحه در حالت فارسی؛
- محتوایی که با Alpine یا fetch بعد از بارگذاری صفحه درج می‌شود.

ریشهٔ مشکل یک‌طرفه بودنِ کار بود: **متن از سرور با رقم لاتین می‌آمد و JS بعد از
paint آن را اصلاح می‌کرد** — اصلاحِ بعد از نمایش، همیشه چشمک دارد.

## ۲) قانون طلایی (قانون اصلی پروژه)

> **ارقام باید از همان لحظهٔ ساخته‌شدنِ متن در خانوادهٔ درست باشند؛ هرگز نباید
> منتظر ماند تا JS بعداً آن‌ها را اصلاح کند.**

- متنِ **استاتیک** (HTML که سرور می‌سازد) → بومی‌سازی **سمت سرور**، قبل از ارسال.
- متنِ **داینامیک** (که JS می‌سازد) → بومی‌سازی **در لحظهٔ درج** (قبل از paintِ همان فریم).
- **ورودی‌ها و داده‌ها** (input/textarea/select، attributeها، script و …) هرگز دستکاری نمی‌شوند.

اگر این قانون رعایت شود، دیگر هیچ عددی «اول انگلیسی، بعد فارسی» دیده نمی‌شود —
در هیچ زبانی و هیچ جای سایت.

## ۳) معماری دو لایه

### لایهٔ ۱ — سمت سرور (ضمانتِ اولین paint)

همهٔ پاسخ‌های HTML از میدل‌ور زیر عبور می‌کنند:

```
bootstrap/app.php → $middleware->web([…, LocalizeHtmlDigits::class])
```

`App\Http\Middleware\LocalizeHtmlDigits` بعد از رندر، کلِ خروجی را به
`App\Helpers\NumberHelper::localizeHtmlText($html, $family)` می‌دهد و فقط
**متنِ بینِ تگ‌ها** را با توجه به خانوادهٔ ارقامِ زبانِ فعال تبدیل می‌کند
(منبع خانواده: `LocaleService::digitFamily()` — همان مقداری که در صفتِ
`data-digits` روی `<html>` می‌نشیند).

نتیجه: مرورگر از **فریمِ اول** رقم‌ها را درست می‌بیند؛ JS نقشی در متنِ
استاتیک ندارد.

### لایهٔ ۲ — سمت کلاینت (محتوای داینامیک)

`resources/js/localize-digits.js` (که داخل `ui-effects.js` سایت و
`app-admin.js` پنل بارگذاری می‌شود):

1. در شروع، یک بار کلِ `document.body` را می‌رود (فقط به‌عنوان تورِ امنیتی —
   معمولاً سرور کار را انجام داده).
2. یک `MutationObserver` گره‌های تازه‌اضافه‌شده را در **همان میکروتسکِ درج**
   تبدیل می‌کند. چون کال‌بکِ observer پیش از render/paintِ همان فریم اجرا
   می‌شود، رقمِ لاتین حتی یک فریم هم نمایش داده نمی‌شود (بدون debounce).

API سراسری که سایر اسکریپت‌ها استفاده می‌کنند (تغییر نکرده):

```js
window.localizeDigits.convert(str)   // تبدیل یک رشته بر اساس خانوادهٔ جاری
window.localizeDigits.walk(el)       // تبدیل کلِ زیردرختِ یک عنصر (فوری)
window.localizeDigits.isPersian()    // آیا خانواده fa/ar است؟
window.localizeDigits.digitFamily()  // persian | arabic | latin
```

### خانوادهٔ ارقام — منبعِ واحد

| محل | مقدار | منبع |
|---|---|---|
| `<html data-digits>` | persian / arabic / latin | `LocaleService::digitFamily()` |
| میدل‌ور سمت سرور | همان | `LocaleService::digitFamily(app()->getLocale())` |
| JS | صفتِ `data-digits` (fallback: `lang`) | سمت سرور |

زبان‌ها: `fa → persian`، `ar → arabic`، `en/tr → latin`.

## ۴) چه چیزهایی تبدیل نمی‌شوند؟ (مهم — امنیت داده)

هر دو لایه (سرور و JS) دقیقاً یک فهرست استثنا دارند:

| مورد | چرا دست نمی‌خورد |
|---|---|
| `input`, `textarea`, `select`, `option` | مقادیر فرم/داده‌ای هستند که ارسال می‌شوند |
| `script`, `style`, `pre`, `code`, `noscript` | کد/داده — تبدیل ارقام داخلشان خروجی را خراب می‌کند |
| `[data-digit-raw]` | اگر عمداً می‌خواهی عددی لاتین بماند (مثل کد) |
| `.hero-num` | اعداد دکوراتیو هیرو که طراح می‌خواهد همیشه لاتین باشد |
| `[contenteditable="true"]` | محتوای ویرایشی |
| صفت‌ها (attribute) و URLها | شامل مقادیر/کدها/توکن‌ها — نباید تغییر کنند |
| موجودیت‌های HTML (`&amp;`, `&#48;`) | ساختار HTML |
| پاسخ‌های غیر HTML (JSON، تصویر، PDF، دانلود، ریدایرکت) | — |

اگر عددی باید لاتین بماند و در متنِ قابل‌مشاهده است، دور آن `data-digit-raw`
بگذار:

```blade
<span data-digit-raw>کد پیگیری: 123456</span>
```

## ۵) قواعد توسعه (وقتی چیز جدیدی می‌سازی)

### متن استاتیک در Blade

**کاری نکن.** همین که عدد را معمولی چاپ کنی کافی است؛ میدل‌ور در لحظهٔ ارسال
بومی‌اش می‌کند:

```blade
{{-- درست: هیچ‌کاری لازم نیست، میدل‌ور بومی می‌کند --}}
<p>{{ number_format($price) }} تومان</p>
<p>{{ show_date($order->created_at) }}</p>
```

### متن داینامیک با JS / Alpine

سه راه (از قوی‌ترین به ساده‌ترین):

1. **داده را همان موقعِ دریافت بومی کن** (توصیه‌شده) — مثل زنگولهٔ اعلان‌ها:

```js
const loc = window.localizeDigits.convert.bind(window.localizeDigits);
items = data.items.map(i => ({
    ...i,
    title: loc(i.title),
    created_at: loc(i.created_at),
    // id / link / url هرگز تبدیل نشوند
}));
```

2. قبل از `textContent`/`innerHTML` مقدار را تبدیل کن:

```js
el.textContent = window.localizeDigits
    ? window.localizeDigits.convert(String(value))
    : String(value);
```

3. یا به observer تکیه کن (درج عادی) — گره همان فریم تبدیل می‌شود. برای
   عناصر بزرگی که دیر ساخته می‌شوند می‌توانی بعد از درج صریح `walk(el)` بزنی.

**قرمز:** عدد را داخل `x-text`/`textContent` لاتین بگذار و انتظار داشته باشی
دیر یا زود درست شود — حتی اگر observer درستش کند، هر کدِ دیگری که متن را
`parseInt` می‌کند روی رقمِ لاتینِ موقت خطا می‌دهد. (الگوهای `parseInt` حتماً اول
با `NumberHelper::persian2LatinDigit`/`toAsciiDigits` نرمال کنند.)

### مقدارهای عددی داخل state/attributes

`x-data="{ count: 5 }"`، `data-id="12"` و JSON همیشه **لاتین** می‌مانند — فقط
نمایشِ متن بومی می‌شود. این جداسازی «داده/نمایش» بخشی از قانون است.

## ۶) چک‌لیست عیب‌یابی (وقتی دوباره چشمک دیدی)

اگر هر جای سایت رقم‌ها اول لاتین و بعد فارسی/عربی شدند (یا در حالت انگلیسی
فارسی ماندند)، به ترتیب بررسی کن:

1. **آیا متن استاتیک است؟** (در HTML خامِ صفحه هست) → خروجیِ سرور را چک کن:
   - `curl http://localhost/page` و جستجوی همان عدد — اگر لاتین است، مشکلِ
     میدل‌ور/فیلتر است؛ اگر فارسی است، مشکل از JS نیست و جای دیگری است.
   - اگر لاتین ماند: آیا صفحه از گروه `web` عبور می‌کند؟ آیا پاسخ `Content-Type`
     غیر HTML دارد؟ آیا اطراف عدد تگ `script/pre/code/select/option` یا صفتِ
     `data-digit-raw`/کلاسِ `hero-num` هست؟
2. **آیا متن داینامیک است؟** (با Alpine/fetch/JS ساخته می‌شود) → در کدِ سازنده
   بگرد و طبق بخش ۵ راه ۱ یا ۲ را اعمال کن (بومی‌سازی هنگامِ ساخت، نه بعد از paint).
3. **آیا صفحه اصلاً localize-digits را بار می‌کند؟** (صفحات guest فقط
   `app.js` دارند — `ui-effects.js` را ندارند؛ آن‌ها کاملاً به لایهٔ سرور وابسته‌اند.)
4. تست‌های مربوطه را اجرا کن (بخش ۷).

## ۷) تست‌ها

- `tests/Feature/LocalizeHtmlDigitsTest.php` — تبدیل سمت سرور در هر ۳ خانواده،
  و این‌که attributeها / script / textarea / select / داده‌ها دست نمی‌خورند.
- `tests/Feature/LocaleServiceTest.php` — خانوادهٔ ارقام هر زبان.
- اجرای کامل: `php artisan test`.

## ۸) نکتهٔ اجرایی

میدل‌ور روی **همهٔ** پاسخ‌های HTML (سایت، پنل ادمین، صفحات guest و خطاهای
داخلِ گروه وب) اعمال می‌شود؛ هزینه‌اش یک پیمایش رشته‌ایِ سبک روی خروجی است.
پاسخ‌های JSON/دانلود/ریدایرکت را رد می‌کند، پس APIها و داده‌های خام همیشه
لاتین می‌مانند.
